## Affected trials: the rule

Added 2026-10-13 ~00:55 UTC at the owner's direction, after trials 1-14 had been seen and
before trial 15 ran. It is a validity rule, not an analysis change.

1. **Definition.** A trial is *affected* if competing compute ran on the machine during the
   trial's window: a test run, lint/format/type check, build, Docker or sandbox job,
   benchmark, or analysis script that is not part of the trial. File reads, searches, text
   edits, git and status checks of about 2 s or less are not competing compute.
2. **Evidence, not results.** Whether a trial is affected is decided from a timestamped log
   of what ran (the session's command log, with each command's start and end), compared
   with the trial's start time and duration. The trial's verdict, change or interval is
   never consulted.
3. **Handling.** An affected trial stays in the record with its result
   (`validation/<set>.json`, `affected` lists it with the reason and evidence). It is left
   out of the primary tally and replaced by one more trial at the end of the same set, so the
   set reaches its planned count of unaffected trials. The report shows a second row with
   the affected trials included, so their effect on every figure is visible.
4. **Going forward.** No competing compute is run by the operator during the remaining
   trials, and each trial records the machine's CPU busy share while it ran (mean and largest
   1 s value) as supporting data; no rule uses that number.
